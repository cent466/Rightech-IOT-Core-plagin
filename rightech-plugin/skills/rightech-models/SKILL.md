# Модели

## Перед генерацией

Порядок обязателен и не переставляется.

1. **Сначала запроси документацию у пользователя.** На запрос «сделай модель»/«нужна модель устройства» первым ответом попроси материалы по устройству: руководство или паспорт, спецификацию протокола (MQTT-топики, JSON-payload, таблицу регистров), таблицу параметров с ключами, типами и единицами, описание команд и примеры реальных сообщений, ссылку на прошивку/репозиторий. Одновременно уточни обязательные `name` (понятное название модели по-русски) и краткое `description` её назначения. Объясни, зачем нужны материалы: из них берутся `reference`, `dataType`, `unit` и тела команд. Если пользователь прислал API Link объекта, поле `model` может помочь определить ID связанной модели, но не заменяет экспорт дерева параметров. Пока документации и обязательных имени/описания нет — не начинай генерацию.
2. **Если документации нет — найди сведения сам** (`rightech-research`): официальная справка Rightech (`base`, `unit`, `idPattern`), сайт и руководство производителя, спецификация протокола, GitHub. Зафиксируй источники (URL, версия/ревизия) и что именно подтверждено.
3. **Сверь с правилами и известными формами** (`references/rules.md`): подбери ближайшую форму по протоколу и типу устройства. Готовые экспорты-образцы в плагин не входят — если формы не хватает, попроси у пользователя экспорт похожей модели из его аккаунта.
4. **Задай остаточные вопросы** (`rightech-questions`) одним сообщением: только то, что не закрыли документация, поиск и образцы — `base`, ключи payload, типы, единицы, команды, подсистемы, события, `idPattern`.
5. **Сгенерируй модель по правилам ниже** и прогони валидатор.

Не при каких условиях не выдумывай параметры, `reference`, единицы, диапазоны и команды: без подтверждения — вопрос, а не догадка. Если пользователь говорит «документации нет, делай как знаешь» — собери минимальную модель только из подтверждённых полей и явно перечисли, что осталось неподтверждённым.

## Оболочка файла

Модель отдаётся файлом-экспортом с обёрткой:

```json
{"version": 1, "origin": "dev.rightech.io", "time": "2026-11-14T12:00:00.000Z", "store": "models", "data": { ... }}
```

`version` всегда `1`; `origin` — хост платформы (`--origin` для своего сервера); `store` — `models`. В `data` обязательны непустые `name` (понятное название модели на русском), `description` (краткое описание назначения), `base`, `data` (дерево), `props`. `_id`, `user`, `group`, `time` внутри `data` — служебные: в export они есть, при создании их выдаёт платформа.

`props` в рабочих экспортах: `bots`, `hardwareEvents`, `idPattern`, `order`, `prefix`, `protocol`, `helper`; в модели пользователя дополнительно `typeInput`, `statusInput`, `descriptionInput`. `props.protocol` повторяет `base`.

## Дерево `data.data`

Корень: `id: "root"`, `type: "subsystem"`, `active: true`, `_inactive: false`, `name` (= имени модели), `children`. В части экспортов у корня есть `base` (совпадает с `base` модели) и `description`.

**Первый дочерний элемент обязателен** — блок внешних модулей; далее идут содержательные подсистемы:

```json
{
  "id": "external-software-modules",
  "name": "Внешние программные модули",
  "active": true,
  "copy": true,
  "type": "subsystem",
  "children": [],
  "_inactive": false
}
```

Блок стоит первым во всех 11 образцах моделей; у Teltonika встречается вариант `id` через подчёркивания. Не переименовывай и не удаляй его, не клади в него параметры.

| Тип | Обязательные поля | Обычно ещё |
|---|---|---|
| `subsystem` | `id`, `type`, `active`, `children`, `_inactive` | `name`, `description` |
| `argument` | `id`, `name`, `type`, `active`, `_inactive`, `source: "state"`, `dataType`, `reference` | `unit`, `factor`, `linear`, `description`, `usage`, `levels`, `display`, `decimalPlaces` |
| `action` | `id`, `name`, `type`, `active`, `_inactive`, `service`, `command`, `params` | `source: "state"`, `dataType`, `description`, `confirm`, `children: []` |
| `config` | `id`, `type`, `active`, `dataType`, `ctrl`, `opts`, `source` | `defaultValue`, `name`, `description` |
| `event-logic` | `id`, `type`, `active` | `name` |

`dataType`: `number`, `string`, `boolean`, `object`. Команды — обычные дочерние узлы подсистемы (например, «Команды управления»), а не массив верхнего уровня.

## Аргумент

`source` всегда `"state"`. `reference` — ключ параметра в данных устройства (`well/telemetry/level`, `in_out_1`); у части образцов он совпадает с `id`. `unit` — из подтверждённого набора платформы: `temperature-celsius`, `speed-kilometer-per-hour`, `electric-volt`, `electric-ampere`, `percent`, `length-meter`, `volume-liter`, `duration-millisecond`, `duration-microsecond`. Единицу не выдумывать: искать в документации устройства, в `GET /api/v1/locale` (поле `units`) или в образце той же величины; если не подтверждено — спросить.

`factor` и `linear` — только при масштабировании: `linear: true` для пропорционального пересчёта, `factor` — коэффициент. Не добавляй их «на всякий случай» с выдуманным значением; если масштаб неизвестен, спроси.

## Действие

```json
{
  "id": "pump_on",
  "name": "Включить насос",
  "active": true,
  "type": "action",
  "source": "state",
  "dataType": "string",
  "params": {"command": "{\"pump_control\": \"ON\"}"},
  "command": "text_command",
  "service": "ric-gate",
  "children": [],
  "description": "Команда на запуск скважинного насоса",
  "_inactive": false
}
```

`service: "ric-gate"`; `command: "text_command"` — текстовая команда, её тело лежит строкой JSON в `params.command`. Для публикации в топик используется `command: "publish"` с `params: {"topic": "...", "payload": "..."}` (+ `qos`). Топик, тело и `command` берутся из документации устройства; не подставляй `publish` вместо `text_command` и наоборот без подтверждения.

## Имена и идентификаторы

Сначала ищи документацию устройства/протокола: таблицу параметров, топики, ключи payload, регистры. Из неё берётся `reference`, а `id`, `name` и `description` строятся по ней так, чтобы человек понимал узел без чтения прошивки.

- `reference` — **точный ключ из документации**, без переименования (`well/pump/voltage`, `in_out_1`, `navigation.speed`). Если документация даёт ключ, не заменяй его «правильным» именем и не переводи.
- `id` — понятное латинское `snake_case`-имя параметра (`liquid_level`, `pump_voltage`, `pump_on`), а не `param1`, `value`, `data`, `p1` и не случайный хэш (`tds-jc5be`). Если документированный ключ содержит `/`, `.`, заглавные буквы или другие символы, переведи его в `snake_case` осмысленно (`well/telemetry/level` → `liquid_level`) и сохрани `reference` как в документации. Уникальность в модели — обязательна; исключение — фиксированный `external-software-modules`.
- `name` модели — обязательное понятное человеку название **на русском**; `description` модели — обязательное краткое описание назначения. Для узлов модели `name` — понятное название на русском (`Уровень жидкости`, `Напряжение питания насоса`, `Включить насос`). Не повторяй `id`, не пиши `Параметр 1` и не оставляй обязательное имя сущности пустым.
- `description` — назначение **на русском**, с единицей и диапазоном/расшифровкой значений, если они известны (`0 - выкл, 1 - вкл`, `Уровень жидкости в скважине, м`). Не выдумывай диапазон: если документация его не даёт, опиши только назначение.
- Названия и описания не переводи на английский и не меняй без просьбы.
- `_inactive: false` — по правилу на каждом узле. В части платформенных экспортов (`model_automatic_aqwa.json`, `model_smart_home.json`) поле отсутствует, поэтому оно не признак корректности платформы, но в генерируемых моделях ставится везде.

Если документации нет или в ней нет нужного параметра — не придумывай ни ключ, ни смысл: спроси название, единицу и формат значения у пользователя.

## Запрещено

- Копировать служебные поля экспорта: `_parentId`, `_isRoot`, `_levels`, `_dataPath`, `user`, `group`, `owner`, `time`.
- Придумывать `reference`, `unit`, `base` или тело команды: только подтверждённые значения либо вопрос пользователю.
- Менять `base` на «похожий» протокол: подтверждены `mqtt`, `nidd`, `teltonika`, `lora`; для остальных нужен эталон или документация.
- Удалять блок `external-software-modules` и складывать в него параметры.
- Оставлять безымянные или невнятные узлы (`param1`, `value`, `data`, имя копирующее `id`): по имени должно быть понятно, что это за параметр.
- Переименовывать документированный ключ в `reference`, если документация даёт его явно.

## Проверка

Проверку запускай bundled-валидатором `scripts/validate.py` навыка `rightech-output`; если кодовый инструмент не видит ресурс другого навыка, сообщи об этом и выполни только структурную проверку, не утверждая, что скрипт запускался.

Покажи пользователю: ближайший образец, отличия от него, число узлов и список параметров. Готовый файл для импорта собирает навык `rightech-output`.
