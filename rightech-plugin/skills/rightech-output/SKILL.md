# Готовые файлы вместо API

Плагин не подключается к Rightech. Результат работы — файлы, которые пользователь сам загружает в интерфейсе.

## Что отдавать по типам

| Тип | Файл | Как попадает в Rightech |
|---|---|---|
| Модель | `<дата>_Модель_<имя>.json` | Создание модели → «Загрузить готовую модель» → файл |
| Сценарий | `<дата>_Сценарий_<имя>.json` | Создание сценария → вкладка «Импорт» → файл |
| Обработчик | `<имя>.json` + `<имя>.js`/`.ts` | Создание обработчика → вкладка «Импорт» → файл |
| Геозона | `<дата>_Геозона_<имя>.json` | Создание геозоны → вкладка «Импорт» → файл |

## Сборка файла

В ZIP скрипты лежат в папке этого навыка: `scripts/make_import_file.py` и `scripts/validate.py`. В Claude Desktop/чате код и ресурсы каждого навыка могут быть доступны в его собственной sandbox-копии, поэтому из навыка `rightech-output` не предполагай доступ к путям другого навыка.

- В Claude Desktop/чате запускай скрипт как путь `scripts/make_import_file.py` относительно папки навыка, например:

```bash
python3 scripts/make_import_file.py entity.json --store models --out-dir rightech-output
```

- В Claude Code/Cowork используй абсолютный путь навыка:

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/make_import_file.py" entity.json --store models --out-dir rightech-output
```

В Codex путь к плагину — `${PLUGIN_ROOT}`. Скрипт валидирует сущность, убирает служебные поля (`owner`, `group`, `time`, `_at`, а в дереве модели — `_parentId`, `_isRoot`, `_levels`, `_dataPath`; `_inactive` и `copy` остаются, как в шаблоне созданной модели), заворачивает результат в оболочку экспорта и сохраняет в `rightech-output/`.

Оболочка повторяет формат платформенного экспорта и официальных примеров импорта, а в `data` обязательно попадает `_id`:

```json
{"version": 1, "origin": "dev.rightech.io", "time": "2026-11-14T12:00:00.000Z", "store": "models", "data": {"_id": "6af9738c82eb553c90e4f072", ... }}
```

**Без `_id` импорт отклоняется с сообщением «Ошибка: неверный формат файла»** — это проверено на живом аккаунте. Скрипт генерирует 24-символьный идентификатор сам; флаг `--id` задаёт его явно, `--user`/`--group` добавляют в оболочку идентификаторы аккаунта (не обязательны), `--origin` меняет сервер.

## Инструкция пользователю

Всегда заканчивай короткой инструкцией под тип:

- **Модель:** «Модели → плюс → Создать → Загрузить готовую модель → выбрать файл (или вкладка «По ссылке») → Создать. После импорта проверьте число параметров».
- **Сценарий:** «Сценарии → плюс → Создать → вкладка «Импорт» → файл → Создать. После импорта назначьте модель объектам и сопоставьте кросс-элементы, как требует платформа». Идентификатор модели в файле должен соответствовать уже созданной модели.
- **Обработчик:** «Обработчики → плюс → Создать → вкладка «Импорт» → файл → Создать; либо вставить код из `.js`/`.ts` вручную. Связи `parameters`/`crossMappings` задайте в интерфейсе: они ссылаются на уже существующие сущности».
- **Геозона:** «Геозоны → плюс → Создать → вкладка «Импорт» → файл → Создать; альтернатива — тип «полигон», GeoJSON во вкладке «Код» и Сохранить». Предложи также отдать список координат текстом.

## Что показать в ответе

Небольшой JSON (до ~200 строк) приведи целиком в ответе вместе с путём к файлу. Большой (модель на сотни узлов, полигон на тысячи точек) — не вставляй полностью: дай путь, размер, сводку и первые элементы.

## Документация перед выдачей

До генерации используй `rightech-research` для самостоятельного поиска неизвестной структуры или деталей устройства. В результирующем ответе коротко перечисли найденные источники; если поиск не нашёл подтверждения, укажи это и запроси недостающий материал. Не подменяй исследование просьбой «загрузите документацию».

## Проверка перед выдачей

1. Запусти `scripts/validate.py` из ресурсов `rightech-output` в той же sandbox-копии навыка (или `${CLAUDE_SKILL_DIR}/scripts/validate.py` в Claude Code/Cowork). Если Claude Desktop держит активные ресурсы в отдельных изолированных копиях и файл не виден, не утверждай, что запускаемый валидатор выполнен: проверь JSON по инструкции и сообщи об ограничении. Для обработчика отдельно укажи: этот валидатор проверяет только структуру JSON, секреты и баланс скобок, а не исполняет/компилирует `userCode`.
2. Покажи, что вошло в файл: имя, тип, число узлов/состояний/точек, отличия от ближайшего образца. Для обработчика добавь таблицу входное поле → модельный параметр → преобразование → выход и сообщи, выполнен ли runtime-прогон на реальном payload.
3. Предупреди, что файл не отправлялся в аккаунт и что импорт выполняет пользователь.

## Запрещено

- Считать, что у геозон нет импорта: вкладка «Импорт» есть в интерфейсе и проверена (2026-11-15), а в документации Rightech её нет.
- Оставлять в файле служебные поля и идентификаторы чужого аккаунта.
- Класть в файлы токены, пароли, ключи.

## SVG и replay моделей

Для иконок или проверки пакетов прочитай [references/model-tools.md](references/model-tools.md).
Все необходимые скрипты, схемы, зависимости и синтетические примеры есть внутри
этого навыка, включая изолированную установку. Запускай из его собственной папки:

```bash
python3 scripts/validate_svg.py icons --strict
python3 scripts/draw_svg.py examples/model-tools/drawings/temperature.json -o icons/temperature.svg
python3 scripts/render_svg.py icons -o rightech-output/svg-preview.png
python3 scripts/replay_cases.py model.json cases.json --out rightech-output/replay.json
```

Кроме XML-проверки, эти инструменты используют зависимости `requirements-tools.txt`.
PNG проверяется просмотром; HTML без PNG не означает успешный рендер.
Replay — ограниченная локальная проверка ожиданий, а не запуск RIC или обработчика.
В ответе раздели статическую проверку, replay, SVG-рендер, RIC и устройство;
`not_tested` не заменяется на `passed` при недоступном инструменте или поведении.
