# Обработчики

## Порядок создания и блокирующие условия

На первый запрос обработчика сначала попроси одним сообщением исходные материалы:

1. **Экспорт модели Rightech с деревом параметров** (`name`, `base`, узлы, `id`, `reference`, `dataType`, `unit`) или её содержимое. Одного имени модели недостаточно: у агента нет доступа к аккаунту, API и `GET /api/v1/models/:id`.
2. **Реальный входной пакет** как есть: топик и точное тело из журнала объекта/устройства. Для бинаря — Base64/hex без обрезки; для JSON — исходная строка. Удалить можно только секреты/персональные значения, сохранив структуру и типы.
3. **Документацию устройства/протокола, если она есть:** точная модель и ревизия, руководство, протокол, таблица регистров/полей, описание команд. Также спроси, что обработчик должен получить на выходе и куда эти значения должны попасть, если это не очевидно из модели и задачи.

Поясни, что модель определяет допустимые параметры результата, а настоящий пакет — фактический формат входа; без обоих входов корректно написать и проверить обработчик нельзя.

### Если документации нет или она неполная

Не проси пользователя искать её вместо себя. Если модель устройства и протокол можно точно определить, самостоятельно запусти `rightech-research`: ищи официальный сайт/руководство производителя, точную ревизию прошивки и спецификацию протокола, а также документацию Rightech по API обработчикам и `handler-libs`. Запиши URL, издателя, версию/ревизию и подтверждённые поля в `references/device-notes.md`. Если точное устройство неизвестно или надёжный источник не найден — назови проверенные источники и попроси только конкретные недостающие сведения.

**Не начинай писать код, пока нет и модели с параметрами, и реального payload.** Найденная документация, похожий образец либо синтетический пример не заменяют ни одну из этих двух вещей. Скажи, чего именно не хватает и где взять: экспорт — в меню модели Rightech; payload — журнал объекта (https://rightech.io/ru/developers/objects/journal) или вывод устройства.

## Сверка до кода

Выполняй только после получения модели и реального payload.

1. Прочитай предоставленную документацию; если её нет/неполная — сначала проведи поиск по правилам выше. Запиши источник, ревизию, формат, единицы, коэффициенты, порядок байтов и коды.
2. Разбери именно реальный payload: топик, формат (JSON, строка, бинарь), фактические поля, типы, пропуски и `null`. Не нормализуй и не «чинить» вход молча.
3. Составь таблицу `поле/смещение пакета → модельный узел (id, reference, dataType, unit) → преобразование → выход`.
4. Сопоставь payload и документацию. Если они расходятся, остановись и покажи обе версии пользователю; не выбирай молча. Если вход содержит поле без узла модели или не предоставляет ожидаемое моделью поле, уточни, должна ли измениться модель либо правила обработки.
5. Подтверди ожидаемый результат на этом payload и поведение для документированных пропусков/ошибок до реализации.

## Код (стиль образцов)

- Точка входа: `export function process(payload)` для JavaScript; `export function process(payload: string, topic: string)` для TypeScript.
- JSON: `JSON.parse(payload)`; не возвращай `undefined` — удаляй отсутствующие поля, чтобы не затирать состояние (`props.setUndefinedParamTo = "prev"`).
- Бинарь: `ric.base64.decode(payload)`, `DataView`, чтение little-endian (`getUint32(offset, true)`), проверка длины перед чтением, диспетчеризация по `classId`, неизвестный id → `{}`.
- Время устройств: эпоха `1980-01-01T00:00:00.000+03:00`, значение = эпоха + секунды × 1000.
- Фрагменты между пакетами: `ric.localStore.forObject.set({...})`.
- Комментарии и типы — на русском. Никаких секретов, ключей и внешних адресов в коде.

## Поля сущности

`name`, `language` (`javascript` | `typescript`), `userCode`, `props`, `description`. Связь с моделью — `parameters["m-<id модели>"]["h-<id обработчика>"].import|export`; для кросс-варианта — `elementType: "cross"`, `crossElements`, `crossMappings`. Точный вид ключей для новой сущности уточни в тестовом проекте.

## Проверка

1. Запусти `process` на предоставленном реальном payload в доступной совместимой среде; сравни фактический результат с согласованным ожидаемым результатом. Покажи вход, существенные шаги преобразования и выход, предварительно скрыв секреты/персональные значения. Если выполнить код в совместимой среде нельзя — прямо укажи, что runtime-проверка не выполнена; структурная проверка её не заменяет.
2. Проверь документированные граничные случаи, которые влияют на этот пакет: короткое/неполное сообщение, неизвестный код, пропущенное поле, `null`, неверный формат. Не придумывай ожидаемое поведение: если его нет в документации, согласуй с пользователем.
3. Проверь итоговый JSON через bundled `scripts/validate.py`. Валидатор проверяет поля сущности, секреты и баланс скобок; сам по себе он **не** компилирует и не исполняет `userCode`.
4. Покажи таблицу соответствия поле → узел → преобразование → выход и перечисли реальные проверки/ограничения. Собери файлы через `rightech-output`: JSON сущности и отдельный файл кода. Импорта для обработчиков нет — пользователь создаёт обработчик, вставляет код и сохраняет.
