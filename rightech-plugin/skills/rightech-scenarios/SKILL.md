# Сценарии

## Перед генерацией

Порядок обязателен.

1. **Сначала собери постановку задачи у пользователя:** обязательны уникальное понятное название сценария и краткое описание его назначения; цель, участвующие объекты, ожидаемые состояния, событие запуска, условия/пороги, действия и конечный результат. Если пользователь описал только цель либо сказал «сделай сценарий» без процесса, не придумывай его и не создавай файл: сначала уточни шаги/состояния и что должно запускать каждый переход (событие, условие, источник и целевое состояние). Предложи заготовку списка шагов, но дождись фактической логики от пользователя. Названия всех состояний — `init`, `state` и `final` — должны быть на русском. Попроси приложить экспорт нужной модели (если используется legacy-режим «по параметрам модели»), спецификацию доступных кросс-элементов, документ/пример события или экспорта похожего сценария, если они есть. Для уведомлений спроси адресата и текст/шаблон; для таймеров — длительность, timezone и поведение отмены.
2. **Выбери тип по документации и ограничениям.** Для нового повторно используемого сценария предпочитай официально рекомендуемый Rightech режим **по кросс-элементам**. Режим **по параметрам модели** устарел, но поддерживается для обратной совместимости и может требоваться для команд из модели с подтверждением/дополнительными параметрами или для чтения параметров события. Если задача требует этих возможностей, объясни причину выбора legacy-типа и попроси точный экспорт модели. Если точный `_id` модели уже известен, запроси его; не подменяй ID именем.
3. **Проведи собственный поиск** через `rightech-research` для неизвестного события, действия, аргументов, условий и схемы Rightech. Когда пользователь дал документацию, читай её и ищи только недостающее/противоречия. Если сведений нет, не придумывай значения; назови, что проверено, и попроси подходящий экспорт/спецификацию.
4. **Сверь с правилами формы** (`references/rules.md`): структура `states`/`transitions` там описана без чужих значений. Готовых экспортов-сценариев в плагине нет — если без примера не обойтись, попроси у пользователя экспорт своего сценария.
5. **Составь спецификацию**: обязательные имя и краткое описание сценария; тип сценария и модели; русские названия состояний; для каждого перехода — подтверждённое пользователем событие/условие и источник → цель; действия в onenter/onexit, аргументы, результат/уведомление, ошибки/повторы/задержки. Для cross-сценария перечисли создаваемые кросс-элементы и правила их сопоставления.
6. **Задай одним сообщением только неразрешённые вопросы**, затем перескажи спецификацию и жди явного подтверждения перед созданием JSON.
7. После подтверждения собери сценарий, проверь валидатором и покажи ограничения проверки.

Не выдумывай `event`, action id/аргументы, `condition`, `processId`, model ID, получателей, сроки и значения порогов. `processId` есть во всех шести экспортах, но официальная схема его создания не найдена: если нет платформенного черновика/подтверждённого ID, не генерируй импортный JSON молча; попроси экспорт пустого сценария из этого аккаунта или официальное правило.

Рекомендуемые официальные источники: [создание и логика сценариев](https://rightech.io/ru/developers/scenarios/create), [общее описание](https://rightech.io/ru/developers/scenarios), [импорт/экспорт](https://rightech.io/ru/developers/scenarios/share), [несколько моделей](https://rightech.io/ru/developers/scenarios/multi).

## Ключевая особенность формата

Поле `data` — **строка**, внутри которой JSON с `states` и `transitions`. Не объект. В legacy-режиме «По параметрам модели» `model` — `_id` выбранной модели, а `models` — список выбранных model IDs. Cross-режим предназначен для повторного использования; модели назначают и сопоставляют с cross-элементами при импорте, поэтому до импорта не требуй единственную фиксированную модель. Экспорт cross-сценария может содержать `model`/`models`, но это не меняет официальный шаг сопоставления при импорте.

```
states:      { "<id>": { "data": { "type": "init|state|final", "id", "name", "width", "height", "onenter": [...], "onexit": [...] }, "position": {"top": number, "left": number} } }
transitions: { "<id>": { "data": { "id", "event", "owner": {"id", "point"}, "target": {"id", "point"}, "condition", "eventParameters" }, "points": [{"x": number, "y": number}, ...], "block": {"layout": {"position": {"x": number, "y": number}, "width": number, "height": number}, ...}, "version": 3, "drawMode": "rou" } }
```

- `owner.id` и `target.id` обязаны существовать в `states`.
- В новом сценарии каждое состояние (`init`, `state`, `final`) обязано иметь непустое `data.name` на русском. Старые экспорты проверяются в совместимом режиме.
- Название сценария `name` и краткое назначение в `description` обязательны. Описание должно быть кратким и конкретным, не заменять собой логику шагов.
- **Координаты обязательны у каждого элемента.** Состояние: собственный `position.left/top` + `data.width/height`; переход: собственный маршрут `points` (минимум две пары числовых `x/y`) + прямоугольник подписи в `block.layout.position.x/y` с положительными `width/height`.
- **Ничего не должно перекрываться.** Прямоугольники state-карточек по `position + width/height` не пересекаются; подписи переходов не пересекают ни карточки, ни друг друга; независимые маршруты переходов не идут одним участком и не пересекаются. Линии могут касаться карточек только в точках своих `owner`/`target`, не проходить через другие состояния.
- `block.layout.position` хранится в координатах сетки редактора; по шести экспортам 1 grid unit = 20 пикселям state/route coordinates. При проверке конвертируй x/y и размеры layout-блока в редакторские координаты (`×20`), не сравнивай разные системы напрямую.
- Если пользователь не дал координаты редактора, раскладывай состояния рядами/колонками по их размерам и выделяй отдельный свободный участок для подписей и маршрутов; рассчитывай `points` из `owner`/`target`, а не ставь всем одинаковые координаты. После генерации валидируй геометрию; при конфликте перестрой layout, не оставляй предупреждение без исправления.
- `type` состояния: `init` (начальное), `state` (обычное), `final` (конечное). Начальное состояние требуется. `final` нужен для завершающегося сценария; официальная документация разрешает его не использовать, если сценарий циклический.
- `event` — имя события перехода. В образцах встречались `init`, `es-recive-device-data`, `immediate-transition`, таймеры `schedule-timer#N-done`, `es-control-timer#N-done` и пользовательские события вида `1st`, `Canteen_exit`. Это наблюдения, не полный каталог. Официальные базовые события описаны в https://rightech.io/ru/developers/scenarios/create; не копируй случайный ID из образца.
- `condition` — строка-выражение; `eventParameters` — параметры события.
- Действия в `onenter`/`onexit`: `[{"id": "<id действия>", "name": "...", "args": {"<аргумент>": {"id": ..., "value": ..., "dataType": ...}}}]`. В образцах: `send-push-message`, `send-telegram`, `change-value`, `create-task`, `gen-user-event`, `timer#N-start|stop`, `schedule-timer#N-start|stop`, а также идентификаторы действий модели.
- Кросс-режим: `elementType: "cross"` + `crossElements` (импортируемые элементы по `tag: "import"`). Без этого — обычный сценарий «по параметрам из модели».

## Что нельзя придумывать

- Каталог доступных `event` и аргументов действий неполон: сверяй системные события/действия с документацией Rightech, пользовательские события — с моделью/описанием пользователя. Если действие или аргументы не подтверждены ни одним источником, остановись и запроси точный экспорт/ссылку или сведения.
- `processId`: есть во всех шести образцах, но схема генерации неизвестна. Не копируй чужой ID и не генерируй случайный. Найди официальное правило; если не найдено, попроси подтверждённый способ получения либо сообщи, что готовый к импорту файл заблокирован этим неизвестным.
- `model`/`models` — ссылки на выбранные модели в экспортах, в том числе в единственном cross-примере. Не подменяй ID именем и не копируй чужой ID. В UI cross-сценарий является переиспользуемым и при импорте требует назначения моделей/сопоставления кросс-элементов; не утверждай, что cross-режим жёстко привязан к одной модели.
- Официально рекомендован режим «По кросс-элементам»; «По параметрам из модели» документирован как устаревший, но временно поддерживается. Кросс-режим не поддерживает параметры полученного модельного события и часть настроек команды (подтверждение/дополнительные параметры); при необходимости таких функций объясни выбор legacy-режима.
- Условия, пороги, получателей сообщений, расписания и действия: используй только значения пользователя или проверенные источники; образец не доказывает, что его значения подходят текущему сценарию. Если пользователь не описал последовательность, обязательно спроси и дождись уточнения шагов и переходов; цель/название/краткое описание не дают права додумывать поведение.
- `position`, `points`, `block.layout.position` — координаты редактора, не бизнес-логика; формат сохраняй по образцу. Их надо генерировать для каждого состояния/перехода, а не пропускать. Координаты, автоматически выбранные агентом, так и обозначай — пользователь их не задавал.

## Проверка

Проверку запускай bundled-валидатором `scripts/validate.py` навыка `rightech-output`; если кодовый инструмент не видит ресурс другого навыка, сообщи об этом и не утверждай, что скрипт запускался.

Валидатор проверяет оболочку JSON, вложенную строку `data`, состояния, переходы, `init`/`final` (final можно пропустить только для намеренно бесконечного цикла), размеры и позиции карточек, отсутствие их перекрытия, координаты маршрутов `points`, позиции/размеры подписей `block.layout`, наложение подписей и пересечения маршрутов, ссылки `owner`/`target`, `event`, `processId` и секреты в `userCode`. Это структурная проверка, не доказательство корректности бизнес-логики и не запуск на живых объектах. Перед сборкой покажи подтверждённую схему `состояние → событие/условие → действие/результат`, тип сценария/модели, cross mappings и неизвестные места. Импорт/запуск на объектах не выполнен — сообщи явно. Импорт сценариев по файлу документирован; после импорта пользователь назначает модели и сопоставляет кросс-элементы.
