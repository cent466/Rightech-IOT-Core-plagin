# Архивный аудит: вопросы до смены подхода

> Этот файл сохранён как история первоначального анализа. Часть вопросов ниже (токен, права, тестовый проект, API-размещение) больше не относится к текущему плагину: сейчас он генерирует файлы без подключения к Rightech. Актуальный список см. в `rightech-plugin/references/open-questions.md`; текущие инструкции — в корневом `README.md`.

Список составлен после офлайн-разбора 24 образцов. Пункты сгруппированы по блокировке: **A** — без ответа нельзя начинать генерацию сущностей; **B** — нужны к этапу размещения через API; **C** — можно уточнить позже, по ходу.

## A. Блокирует генерацию

| № | Вопрос | Почему нужен | Как ответить |
|---|---|---|---|
| A1 | Целевая среда: Claude Code локально, маркетплейс или иное? | От неё зависит структура плагина, вызов навыков и проверка манифеста | Одно предложение |
| A2 | Есть ли отдельный **тестовый** проект Rightech? | ТЗ требует сначала проверять в тестовом, а не в рабочем | Имя проекта |
| A3 | Какой сервер: `https://dev.rightech.io` или on-premise? | Адрес попадает в `RIGHTECH_BASE_URL` и в примеры | URL |
| A4 | Политика токена: полные права, как в ТЗ, или минимальные `scopes`? | Токен с полными правами может удалить всё в проекте | Вариант + срок жизни |
| A5 | Формат круглой геозоны | В образцах только полигоны; выдумывать формат нельзя | Экспорт одной круглой геозоны из аккаунта (JSON) |
| A6 | Нужен ли в моделях тип узла `event`? | В образцах его нет ни разу | Да/нет; если да — экспорт модели с событием |
| A7 | Какие действия сценариев поддерживать в первой версии? | В образцах встречается 10 видов действий, полного каталога аргументов нет | Список: `send-telegram`, `send-push-message`, `change-value`, `create-task`, … |
| A8 | Нужны ли платформенные поля узлов (`_parentId`, `_inactive`, `copy`, `_isRoot`) в API? | От этого зависит сборка дерева модели при создании | Ответ после проверки в тестовом проекте; можно отложить до этапа API |

## B. Нужны к этапу размещения через API

- B1. Токен в `RIGHTECH_TOKEN` (или локальный файл) — **только после** того, как код будет готов к dry-run. В чат токен не присылать.
- B2. Разрешение на один контролируемый тест в тестовом проекте: создать сущность, прочитать её, удалить созданное.
- B3. Эталон ответа `POST` для каждого типа (или разрешение снять его самостоятельно в тестовом проекте): что возвращает сервер, какие поля обязательны фактически.
- B4. Лимиты: размер полигона, число узлов модели, длина `userCode`.

## C. Уточнить позже

- C1. Правила именования сущностей в вашей организации (префиксы, язык `name`).
- C2. Нужны ли описания (`description`) на русском у всех сущностей.
- C3. Язык обработчиков по умолчанию: JavaScript или TypeScript.
- C4. Есть ли собственный маркетплейс или публикация не требуется.
